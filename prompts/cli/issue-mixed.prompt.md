# Mixed area decisions and part issues

Own src/issue-mixed.mjs. Preserve single-area routing. All I/O uses injected ports.
resolveMixed({snapshot,issue,record}) returns null for a single area, otherwise
{action,area,owner,reason,parts}. parts are {state,area,owner,source} rows from
resolveAreas. Complete touchedAreas evidence must agree with matched areas;
unknown areas or missing evidence mean question with needs-owner. Distinct owners
require a whole or split policy. Locally owned areas alone may work together.

An issue sortOwnerChoice is empty, whole, split or conflict. The dependency reader
computes it through readOwnerChoice({labels,comments,timeline},authorityFor).
Only trusted requirement comments count. Accept pdd:owner-whole, pdd:owner-split,
"mixed: whole|split", "owner: whole|split", or "whole issue"/"split this issue" as
standalone directives, case insensitive. Ignore quoted text and code fences.
Use the latest trusted directive. Active owner labels override comments and area
defaults. Both labels conflict. Verify the latest label event actor as trusted;
missing or untrusted provenance means conflict, never authority. Explicit areas'
mixed defaults must agree for their external owners. For promptdriven/pdd only,
an external area named runtime defaults to whole when mixed is absent. A whole
choice requires exactly one distinct external login owner; repository-only owners or
competing owners ask. A split requires exactly two areas, one autopilot owner,
one external login, and splitOrder naming either area with evidence.

syncMixedParts({cwd,repository,snapshot,mode},ports,write) uses the caller's paced
20-write stream. Auto creates two part issues titled "<area> part of #N" so each
part can close independently and local-first order cannot deadlock on the parent.
Each body names the parent, scoped evidence and an exact pdd-issue-part:v1 marker
with JSON {parent,area}. Before creating, recover exactly one trusted marker from
all pages of github.page kind splitCandidates (the issue index in all states). Use shared withSortGroupAdmission per parent
and area, then reread under admission. Never duplicate an uncertain POST. A proven unsent failure releases shared admission through the paced writer; a failed transport or readback retains it. Native creation errors expose sortUnsent:true only if transport was never invoked. Assign
the external part only after confirming all links, with an ownership guard. Link both as native sub-issues, block the parent by
both, and block the later part by the earlier one. Confirm each relationship by
readback. Do not change any existing child with an assignee or live claim; initial
assignment after link confirmation is permitted. Recover relationships without writing them
again when already present. Stop on uncertain writes or duplicate markers.
An interrupted split may recover a known child that is closed with state_reason
completed. If unassigned and unclaimed, confirm its missing relationships and
persist the split without assigning completed work. Never replace that child.
Other closed states do not authorize missing relationship writes. Existing
confirmed links and the expected external assignment remain resumable.

Write one immutable parent route note with marker pdd-issue-split:v1 and JSON
{parts:[{issue,area}],first}. The reader retains this as issue.sortSplit only from
trusted intact comments with valid same-repository child identities, unique areas
and two distinct children. Conflicting records hold. partIdentity(body) returns
{parent,area} or null; readSplitComment(comment,authority) returns the split or null.
The reader observes recorded children even when closed. A part stays held until
its trusted parent's confirmed split includes it. Native dependency order still
controls its start. The parent stays held until both children have completed;
Native state_reason must be completed for both children. The reader exposes sortCompleted as true only for closed children with that explicit reason; missing, null, not-planned, unknown, absent or unreadable children do not count as done. Closing
the parent respects ownership, pacing and current child completion. After all
split notes, trust, timeline and child completion reads, reread parent claims and
the issue. Require an open state, known empty assignees, no live claim or working
label, and unchanged title, body and labels. This final check also runs inside
native mutation admission; unknown or changed ownership stops closure. Observe
proposes split work without creating, assigning or linking children. Questions
use the ordinary one-note needs-owner route. A later choice change on an already
split parent asks a person; do not silently orphan parts or start duplicate work.

Before every effect after pacing, reread parent ownership, current mode and sort
inputs; never touch a person-assigned or live-claimed parent. Check both relationship endpoints before
relationship effects and again inside native mutation admission. Unknown ownership
holds. Finish sort and trust evidence validation before final endpoint ownership
observations. Read claims for all affected children before their final issue
observations, then reread parent claims and issue state. A child needs known empty
assignees, no live claim or working label, and an open or explicitly completed
state for missing links; assignment requires open state. For an ordering link,
validate both children together so the second child's claim read cannot hide a
person assignment on the first. The final parent observation requires unchanged
title, body and labels, open state, known empty assignees and no live claim or
working label. These checks also run inside native admission after any wait;
changed ownership stops transport. The separate remote observations cannot
eliminate changes after the last read.
Native github.createSortPart({repository,title,body,assignee?,checkOwnership}) returns
{json} after confirming title, body, identity and assignment. github.ensureSortLink
({repository,issue,childId,kind,checkOwnership}) returns {ok}; kind is sub or blocker.
It reads the relationship before writing and confirms after the guarded POST.
Creation, links, reservations and notes use the same paced writer and native budget.
