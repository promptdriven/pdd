# Runtime output

Own `src/runtime-output.mjs`. It turns `pdd check` rows into the terminal table, the `--json` object and the exit code. It makes no call and writes no file.

## Rows

A row is one test: `story`, `title`, `test`, `state`, `checks {passed, total}`, `failed_checks [{criterion_id, step_id, criterion_text, target, path, expected, actual, diagnosis}]`, `refusals [{code, section, message, engine_message, hint, reason, fix, where, cause}]`, `calls`, `seconds`, `requested_model`, `report_url`, `request_id`, and diagnosis fields `why`, `who`, `next_step`. A confirmed unstarted capacity row has `busy:true`, `can_retry:true` and state `not_run`; it is not a source refusal or failed assertion. Render its capacity advice without a Fix-the-test line and mark a summary containing only passed rows and actual busy rows (with at least one busy row) `busy`, not ✗. Mixed actual failures retain ✗. Preserve request ID, report and zero-call accounting. States: `passed`, `failed`, `refused`, `not_run`, `unknown`, `queued`, `running`.

- From a server answer: checks come from `result.report.samples[0].steps[].checks[]`; refusals from `result.refusals` (prompt-runtime #379 adds `reason` in plain words, `fix`, `file`, `at`, `where` = file and place as one text, and `cause`: `call-budget`, `ai-service`, `test`, `prompt`, `server` or `unknown`; `where` falls back to `file` and `at`; each is null when missing); calls from `usage.calls`; the model from `usage.requested_model` (else the report's `evaluation.requested_model`). pdd uses `state`, not `outcome`.
- Incomplete accounting (`usage.accounting_complete:false`, report `accounting_complete:false`, or positive `usage.unknown_calls`) never projects a complete numeric row call total, even when `usage.calls` is numeric. Preserve a valid known lower bound (`usage.known_calls`, else numeric `usage.calls`) in summary totals and append the unknown part, for example `2 AI calls + 1 unknown`; absent unknown-count detail still contributes an unknown component. Keep row `calls` unknown and retain the existing public summary format. Pending or unavailable usage remains unknown; only positively unsent work defaults to zero.
- Seconds are rounded to 0.1.
- Expected and got values that fit on one line print as JSON on the check line, so strings are quoted and escaped (`"Sam\n"` differs from `"Sam"`). They fit when no string has a line break before its end and each JSON is at most 80 characters.
- Other values (round-2 tester: a CLI's stdout lost its line breaks and was cut near the difference) print as a block under the check line: `    expected:` and `    got:`, each followed by its lines, 6 spaces in. A string shows its own lines with no quotes, and `(ends with a line break)` when it ends with one; any other value shows as JSON with 2-space indents. pdd never cuts inside a line. A value shows at most 20 lines: from line 1, or from 2 lines before the first line where two strings differ when that line is later. Lines left out are named: `… N lines before` above, `… N more lines in the report` below. Each line loses control characters and the token but keeps its spaces.
- Clean all server text: remove control characters, the token and server paths (`/home/…`, `/srv/…`, `/var/…`, `/tmp/…` and similar). Expected and actual values keep their JSON type but lose the token.

## Exit code

The first match from the top wins:

| Code | When |
|---|---|
| 3 | A row is unknown, queued, running or in any state that is not a known end, the lint result is unknown, or Ctrl-C |
| 5 | A row was not run (sign-in, gate, server busy at the time limit or when pdd stopped, no AI room) |
| 4 | A row was refused (local preflight, lint or engine) |
| 1 | A row failed |
| 0 | All passed |

## Text (stdout)

1. Exit 3: the first line is `pdd check --read <batch>`.
2. The table: `Story`, `Test`, `Result`, `Checks`, `Time`. Story = the story title. Result `not run` for `not_run`; a draft row adds ` (DRAFT)` to its result and to its report link line. Checks `n/m` or `-`. Time `21.0 s` or `-`.
3. One paste line per Story (0.1.6, many Stories in one run), in table order: `Runtime check (<story>): ✓ 3 of 3 criteria · 10/10 checks · 1 AI call`, with ` (DRAFT)` after the story when a row of it ran a draft prompt; a Story with two test files gets one line for both. With one Story, its line is the only Runtime check line (round-2 tester: no second line that repeats it). With two or more Stories, the overall summary line comes last of these lines, one line that an agent can paste into a PR: `Runtime check: ✓ 3 of 3 criteria · 10/10 checks · 1 AI call`; `Runtime check (DRAFT): …` when a row ran a draft prompt. Use the summary mark rule below for both Story and overall lines. Criteria come from the report's `criterion_results`; a row with no such list counts its test's criteria, all passed only when the row passed. Rows that are refused, not run, unknown, queued or running add `· N refused` (and so on). Calls count only ended rows; others add ` + N unknown`.
4. A block for each problem row, failed rows first. For refused, not-run and unknown rows, show each supplied nonempty server `why` as `Why:` and `next_step` as `Next:`, using the existing text cleaning. The client supplies accepted server advice under its no-verdict explanation rule; client-generated transport reasons remain valid fallback explanations. Each field overrides only its corresponding fallback: why-only keeps existing next-step advice; next-step-only keeps the existing explanation and removes only a conflicting retry sentence. For NOT RUN, preserve the true busy explanation when a request was sent; never claim it was unsent, remove the whole explanation, or leave a dangling colon when advice replaces it. With neither field, preserve the existing block. A server next step suppresses conflicting client retry/fix advice, including refusal Fix/hint instructions and the AI-service/provider "run again" lines; keep refusal codes, causes, locations, reports and IDs.
   Existing fallback blocks:
   - `FAILED  <title> (<test>)`, one line for each failed check `  AC1  step place-order  result /totalCents  expected 899, got 900` (or the check line `  AC1  step place-order  result /stdout` and its block), followed by a `Criterion: …` line when the authored criterion is at most 160 characters, the row warnings, and then the report link. For target `error`, say `got no error (a normal result)` only when the step has a result and no error, or diagnosis kind `no-error`/`needs-tool`; otherwise keep `{"missing":true}`. Print each failed check's own `Why:` and `Next:` pair from its diagnosis. With no diagnosis, use the failed row's run-level fields when both are present; otherwise say `Next: show this check to the person. A person decides expected values. The agent may propose a change, and never makes it.` For a failed step with rerun diagnosis or a matching report rerun, print one `Rerun:` line under its first failed check; `Rerun: failed N of M (stable). A recheck of the same files will not help.` or `Rerun: failed N of M (unstable). Make the rule in the prompt firmer.`; `failed 0` is `passed M of M reruns.` and `runs: 1` prints no verdict. Rerun lines carry no call count; rerun calls appear only in the summary line as `(N for reruns)`. A skipped rerun says `Rerun: skipped (<reason>).`
   - `REFUSED before sending (not sent, 0 AI calls)`, then for each row `  <test>  step N  <code>` and the message and hint lines.
   - `REFUSED  <title> (<test>)`, then for each refusal with a `reason`: `  <code>: <reason>`, `  Where: <where>` when there is one, and `  Fix: <fix>`; when `cause` is `ai-service` the last line is `  Your test is fine. Run it again.` in place of the fix. A refusal with no `reason` (the live server before #379) keeps `  <code>  <section>  <message>` and the engine message when it adds detail. Both end with the `pdd:` hint when there is one.
   - `NOT RUN  <title> (<test>): <message> (<code>)`.
   - `STILL RUNNING after <limit>: <title>. Do not send it again.` at the time limit; the limit is `90 s` for the agent default, else `N min` (after Ctrl-C: `STILL RUNNING when pdd stopped reading: …`; in `--read`, or with no known limit: `STILL RUNNING: …`)
   - `UNKNOWN  <title>: the run may have executed. Its result is unknown.` and the server's reason.
   - An AI provider failure (state `unknown` with `graph-provider-failure`, or a sample `failure_cause.kind` of `transport_unknown`) has its own block: `UNKNOWN  <title>: the AI provider failed during the run. It is not a failed check. Do not send it again yet.`, then the code, the cause and the report link. The block ends with `To try again, run \`pdd check\` again (a new request).` pdd never resends it.
5. With `--details`: every check of each row, failed checks first.
6. `X of Y stories passed. Model asked for: M.` Skip the model part when it is not known. Time is shown only for ended rows.
7. `Reports (anyone with a link can open it):` and one `  <story>  <url>` line for each row with a link.

## Summary mark and mixed exits

Apply this precedence to every summary: any failed row → `✗`; otherwise a nonempty set of all passed rows → `✓`; otherwise any queued/running row → `running ·`; otherwise any refused, unknown, or nonbusy not-run row → `no verdict ·`; otherwise a set containing at least one actual busy row and consisting only of passed or actual busy rows → `busy ·`; otherwise → `no verdict ·`. An actual busy row has state `not_run` and `busy:true`; stale busy flags on other states never make them busy. Empty rows have no verdict. Running mixed with refused remains running; passed mixed with actual busy remains busy. Keep counts, draft marks, calls and ordering.

Exit precedence is unchanged. Only when a failed row and an actual inconclusive row are both present and the batch exits 3, 4 or 5, print one notice after the summaries. An exit-3 flag such as interruption or lint uncertainty with only passed/failed rows does not authorize a no-verdict claim. Count distinct Story identities with a failed row, and distinct Story identities with an inconclusive row contributing to the higher-priority exit: refused, not-run (including busy), unknown, queued, running or another nonterminal state. Multiple rows of one Story count once in each applicable set.

When an inconclusive Story is outside the failed set, use the brief's ordinary wording: `1 Story failed its checks. Another Story has no verdict, so the exit code is E.` For plural counts substitute `N Stories failed their checks` and `M other Stories have no verdict`; retain `Another Story has no verdict` when exactly one qualifying Story is outside the failed set. Count these other Stories once; an overlap with a failed Story does not increase the other-Story count. When there is no other inconclusive Story, use the truthful overlap wording: `1 Story failed its checks. That Story also has checks with no verdict, so the exit code is E.` For multiple failed Stories use `N Stories failed their checks. M of those Stories also have checks with no verdict, so the exit code is E.`; if M is one, use `1 of those Stories also has checks with no verdict`. E is the actual batch exit. Busy and open rows can cause this notice even though their summary mark remains busy or running; notice eligibility is separate from mark precedence.

## JSON (stdout, `--json`)

One object: `{batch, repo, exit_code, summary_line, draft, rows: [{story, title, test, state, checks, criteria, failed_checks, refusals, calls, seconds, requested_model, report_url, request_id, draft, reason, why, who, next_step, rerun, summary_line}], warnings}`. Failed checks carry `diagnosis`, including any check rerun data; failed rows carry the first failed check's diagnosis when the run-level fields are empty, plus failed-state `who`. Preserve supplied `why` and `next_step` for failed, refused, not-run and unknown states. Refusals retain their `cause`. `reason` is `{code, message}` for a row that was not run or is unknown (`graph-provider-failure` for a provider failure), else null; passed and failed rows keep `reason` null. Preserve report-level `rerun` for the applicable state, otherwise null. `usage.calls` is the total including rerun calls; `rerun.calls` is the rerun share, shown in the Runtime check line as `(N for reruns)`. When usage is missing, omit the unknown total rather than printing zero. A row's `summary_line` is the paste line of its Story. `draft` is true for a row that ran a draft prompt, and at the top when any row did. When the server answer has `draft_prompts` (a list of repo paths), a nonempty list means DRAFT and an empty one means not DRAFT; it wins over pdd's local guess. Older servers without the field keep the local guess. Nothing else goes to stdout.

## Dependencies

Read the full [Prompting guide](../../docs/prompting-guide.md) before you change this prompt. The [runtime client](runtime-client.prompt.md) builds the rows and prints this output.

Saved check JSON includes source_sha256 (full captured upload hash, null when no capture) so workflow evidence can verify it against the exact selected source.

## Try usage
Export tryUsage(answer, {cap}={}), tryUsageLine(usage, {command=false}={}) and tryUsageHeaders(usage). Normalize only nonnegative safe-integer counts; absent/malformed counts are unknown, never invented zero. Owner model calls.cap/remaining, session.max_calls/remaining_calls and call usage.calls/report.remaining_calls are the existing server fields. Derive cumulative used only from valid cap and remaining <=cap; this is the Try session allowance, not a machine/account/tester allowance. Format a short startup/session line and per-command line that distinguishes this command's calls, session used, remaining and cap, with unknowns explicit. HTTP header names are x-pdd-ai-calls, x-pdd-try-used, x-pdd-try-remaining and x-pdd-try-cap; values are decimal integers or unknown. These headers are owned metadata and cannot come from program result headers.

## Progress and causes
Every pdd command reports progress and errors through these two helpers, so all progress has one style.
- Export `progressTicker(stream, now, everyMs = 15000)`. A slow step (more than about 2 s: network, lint, upload, the queue, AI calls, git, gh, Herdr, an agent) first prints one plain line that ends with `…`, for example `Checking 3 files (29 KB) on the PDD interpreter (lint, 0 AI calls)…`. The returned `tick(text)` prints `<text> · <time>` at most once every `everyMs`, counted from the start, with the time from `sinceText` (`N s` under a minute, else `N min`). Each step ends with a clear line: the result, or `Try ready: <link>`.
- Progress goes to stderr only, never to stdout, so the result and `--json` stay clean. A person and an agent (no terminal) get the same lines: no spinner, no carriage return, no colour codes.
- Export `causeText(value, secrets = [])`: the first nonempty line of a tool's or server's error text, with control characters, the given secrets and GitHub or API tokens removed, at most 300 characters. An error line says what failed, this real reason, and what to do next.

## Step time limits

Export `stepTimeLimit(answer, {steps=[], secrets=[]}={})` to recognize a server step time refusal from raw report/sample/step refusals. The published server currently reports legacy `graph-provider-failure` with explicit timeout/timed-out/time-limit detail (including failure_cause.detail or legacy failure_cause.kind timeout); do not classify a generic provider failure, queue wait or client polling deadline as a step limit. A typed failure_cause.kind `step_timeout` also identifies a step limit independent of its code. No dedicated new code is assumed until the runtime publishes it.

Identify the step by its reported step_id/name, otherwise a valid steps[N] refusal section mapped to authored step IDs (including the sole matching companion refusal section when raw sample metadata omits it), otherwise say unnamed step. Preserve/sanitize the server-provided name. Use an explicit positive timeout_seconds/limit_seconds from the refusal or its details, otherwise a timeout detail's explicit seconds/minutes; legacy default is180seconds. A typed step_timeout without a reported duration uses the requested600second policy. Never infer the time limit from total job elapsed time. Return code, step, minutes and the message `Step NAME took more than N minutes and was stopped.` plus `Make the step smaller, for example split 30 moves into 3 steps of 10.`

This is inconclusive execution, never a failed expectation. Project it as unknown with structured time_limit and reason, retaining actual usage, earlier check evidence and report/ID. In text, give a STOPPED block with that step message and advice, suppress the generic provider-failure/failed-expectation framing for this refusal. Other provider failures retain existing behavior. JSON contains the same message and structured time_limit. No automatic retry is authorized.

## Module binding coverage

Check and lint results with supplied coverage print `N of M modules bound`, followed by each selected unbound module path, reason and attempted port. JSON includes `coverage: {available, bound, total, modules}` with each module's path, state and, when unbound, reason and port_attempt. Unknown inventory prints `Module binding coverage unavailable: no pdd-bindings.json.` and has available:false, bound:null, total:null, modules:[]. Binding measures declared executable coverage for selected Stories, not a count of passed modules. Preserve all ordinary check/lint results and exit status.
