# Runtime output

Own `src/runtime/runtime-output.mjs`. It turns `pdd test` rows into the terminal table, the `--json` object and the exit code. It makes no call and writes no file.

## Incomplete selected tests and criteria

Rows can carry `unsent:true` and `not_checked:[{criterion_id,text,reason}]` from local validation. JSON retains both. List locally broken unsent rows first as `not run (broken-test)` in text and JSON, with their file, reason and fix hint before other results. Count them in each applicable summary as `N tests could not run`. Preserve other summary and exit precedence rules.

For each not-checked criterion print `ID: not checked: <reason>` and its text. It is never a passed criterion. Keep its place in the full Story total, exclude its ID from reported passed counts, and retain other checked results and real usage. A run with any such criterion is not a full Story pass; say so in text and summaries. A server pass becomes `not_run` at the client boundary; failures and other inconclusive states retain their existing meaning. Saved reads render the same facts.

## Rows

Preserve an optional `path` on each local shared-reader refusal in `jsonRow`.
It names the affected repository-relative prompt, including a called prompt.
Omit it when absent; keep all existing refusal fields and cleaning rules.

A row is one test: `story`, `title`, `test`, `state`, `checks {passed, total}`, `failed_checks [{criterion_id, step_id, criterion_text, target, path, expected, actual, diagnosis}]`, `refusals [{code, field, section, message, engine_message, hint, reason, fix, where, cause, dependency_errors?}]`, `calls`, `seconds`, `requested_model`, `report_url`, `request_id`, diagnosis fields `why`, `who`, `next_step`, and the outcome fields `progress` and `ahead` when the server supplied them. When usage accounting is known, JSON may also include `known_calls`, `unknown_calls` and `accounting_complete`. A complete receipt keeps its numeric `usage.calls` total even when `known_calls` is lower. Incomplete multi-ID usage keeps `calls` unknown and reports the summed known lower bound and unknown count. A confirmed unstarted capacity row has `busy:true`, `can_retry:true` and state `not_run`; it is not a source refusal or failed assertion. Render its capacity advice without a Fix-the-test line and mark a summary containing only passed rows and actual busy rows (with at least one busy row) `busy`, not ✗. Mixed actual failures retain ✗. Preserve request ID, report and zero-call accounting. States: `passed`, `failed`, `refused`, `not_run`, `unknown`, `queued`, `running`.

- From a server answer: checks come from all samples in `result.report.samples[].steps[].checks[]` in sample and step order (with `result.failed_checks` projected and cleaned as fallback when `report.samples` yields no failed checks, and valid `result.checks` `{passed, total}` retained when `report.samples` has no checks); refusals from `result.refusals` (prompt-runtime #379 adds `reason` in plain words, `fix`, `file`, `at`, `where` = file and place as one text, and `cause`: `call-budget`, `ai-service`, `test`, `prompt`, `server` or `unknown`; `where` falls back to `file` and `at`; each is null when missing); calls from `usage.calls`; the model from `usage.requested_model` (else the report's `evaluation.requested_model`). pdd uses the canonical selected outcome, not the server's display `outcome` string.
- In `projectAnswer(answer, options)` (for a single server check answer), numeric `calls` and `provider_calls` count total dispatched calls for that request (`known_calls + unknown_calls`), not confirmed completed calls alone. Let reported `unknown_calls` be the maximum valid nonnegative integer `unknown_calls` across supplied surfaces (`0` when absent). When explicit valid `known_calls` is supplied, `known_calls` is the maximum valid `known_calls` across supplied surfaces and is never clamped up to `calls` or `provider_calls`; when no valid `known_calls` is supplied, derive `known_calls` from the maximum valid `calls` and `provider_calls` after subtracting reported `unknown_calls` (floored at `0`), defaulting to `0` when none is supplied. Incomplete accounting (`accounting_complete:false` on any supplied surface, conflicting or malformed counters/flags, missing numeric `usage.calls`, explicit `known_calls` above `usage.calls`, `provider_calls` above `usage.calls`, or positive `unknown_calls`) never projects a complete numeric call total, even when `usage.calls` is numeric: `projectAnswer` returns `calls: "unknown"`, `known_calls` (the disjoint lower bound), `unknown_calls: max(1, reported unknown_calls)` and `accounting_complete: false`. Complete accounting returns numeric `calls` (`usage.calls`), `unknown_calls: 0` and `accounting_complete: true` (omitting `known_calls` on `projectAnswer`, which `jsonRow` normalizes to `known_calls: null` when `accounting_complete` is present). Across restart/capacity IDs, the client sums each ID's disjoint known and unknown components; a later complete replacement cannot erase earlier incomplete usage or its raw receipt. In `jsonRow` and `summaryLine`, a row is a sent row exactly when `row.phase === "server" || Boolean(row.request_id) || row.state === "sent"`; non-sent rows (including pre-send local rows and minimal `renderJson` rows that omit `phase: "server"`, `request_id` and `state: "sent"`) get `calls: 0` and add `0` calls and `0` unknown calls.
- Export `tokenUsageOf(answer, {incomplete=false}={})` and project `input_tokens`, `cached_input_tokens`, `output_tokens` and `cached_input_share` onto each answer view and JSON row. Validate only nonnegative safe integers from `result.report.model_usage` (using current-run calls/totals when `complete` is true, excluding `historical` replay calls, and treating `complete:false`, `coverage.accounting_incomplete:true`, `transport-uncertain` or `pre-dispatch` current calls as unavailable) and/or `usage` (`input_tokens`, `cached_input_tokens`, `output_tokens`), with `cached_input_tokens <= input_tokens`. `cached_input_share` is `cached_input_tokens / input_tokens` in `0..1` when `input_tokens > 0` and both counters are valid integers, and `null` when `input_tokens === 0` or either counter is `'unknown'`. Distinguish measured `0` cached tokens (`cached_input_tokens:0`, `cached_input_share:0` when `input_tokens > 0`) from `'unknown'` / `null` (unavailable, incomplete or pre-dispatch) and from zero input (`input_tokens:0`, `cached_input_tokens:0`, `cached_input_share:null`).
- Seconds are rounded to 0.1.
- Expected and got values that fit on one line print as JSON on the check line, so strings are quoted and escaped (`"Sam\n"` differs from `"Sam"`). They fit when no string has a line break before its end and each JSON is at most 80 characters.
- Other values (round-2 tester: a CLI's stdout lost its line breaks and was cut near the difference) print as a block under the check line: `    expected:` and `    got:`, each followed by its lines, 6 spaces in. A string shows its own lines with no quotes, and `(ends with a line break)` when it ends with one; any other value shows as JSON with 2-space indents. pdd never cuts inside a line. A value shows at most 20 lines: from line 1, or from 2 lines before the first line where two strings differ when that line is later. Lines left out are named: `… N lines before` above, `… N more lines in the report` below. Each line loses control characters and the token but keeps its spaces.
- Clean all server text: remove control characters, the token and server paths (`/home/…`, `/srv/…`, `/var/…`, `/tmp/…` and similar). Expected and actual values keep their JSON type but lose the token.

## Reported predecessor errors

For a completed Check refusal, add only the dependency facts established by the
raw report and the captured authored steps supplied to `projectAnswer`. This is
an additive diagnosis. Keep the server refusal and all outcome, check identity,
criterion/check count, usage, model, exit, recovery and dispatch facts unchanged.
Do not mutate either input, make a call, write a file, resend work or derive retry
authority from an application error code. A generic refusal or missing step does
not establish that dependent work was unexecuted.

Associate a refusal only through its exact `samples[N].steps[M]` section, within
the report sample bounds and captured authored step bounds. A relative `at`
location such as `steps[M]` may corroborate the step index only when the exact
section anchors its sample. Any other supplied sample/step location must agree.
A bare step location without that section, conflicting location, missing authored
input or missing/malformed/duplicate authored dependent identity yields no fact.
A reported dependent row may be absent because input resolution refused; this
absence supplies no dispatch claim. When that row exists, its identity must match
the authored step at M. Never select another sample by matching an ID.

Walk that authored step's `input` in authored object/array order. An exact
reference object has only `$step_result`; its value has exactly string `step_id`
and `path` fields. Do not interpret strings, messages or objects with extra keys
as references. The predecessor ID must uniquely identify an earlier authored
step and exactly one completed reported predecessor in the same sample. Require
a nonblank reported `error.code` string and an absent or null normal `result`.
Any non-null normal result, including false or zero, conflicts with that error
and suppresses the fact. Missing, malformed, duplicated or redacted predecessor
identity/code evidence supplies no fact. No transitive chain is inferred.

An associated refusal may carry `dependency_errors`, an optional nonempty ordered
array. Each item has exactly five string fields: `step_id` (dependent authored
identity), `input_path` (JSON Pointer within its input), `predecessor_step_id`
(referenced authored identity), `result_path` (the authored result pointer), and
`error_code` (the predecessor's reported code). Include distinct input references
in traversal order; two different input pointers remain distinct. Escape input
pointer tokens as `~0` for `~` and `~1` for `/`. Omit the field when no supported
fact remains; never add null placeholders or an invented code.

Before publishing every added string, apply existing control-character and known
secret cleaning and the recognized credential-token pattern. Apply server-host
path cleaning to identities and codes. Preserve reference pointers as pointers,
while removing embedded secrets and controls; do not redact them as host paths.
Do not publish application error payloads, traces, worlds or resource data.

`jsonRow` and `renderJson` retain this optional field on the existing refusal.
After its existing refusal lines, text prints one line per fact with JSON-quoted
string values, exactly:
`  Dependency: step "draw-refusal" input "/loaded" references step "unknown-order" result "/loaded"; that step reported error code "board-unavailable".`
The five values vary with the fact. Keep the `Dependency:` label and punctuation.
This reports an authored reference and an observed code, without claiming a cause
or dispatch status.

Saved batch reads with the original receipt and captured authored steps show the
same facts. UUID-only and old reads without authored references preserve the
existing refusal and omit this diagnosis. Current source cannot replace captured
authored input for attribution. The minimal partial `renderJson` entry below
checks retention of already projected facts only; native public-boundary tests
must check report association, cleaning, terminal output and saved reads.

## Criterion check facts

The existing module functions `renderJson(options)` and `renderText(options)` use each row's authored `steps[].checks` and `criterion_texts`, already retained for immediate and saved/read results. For each criterion identity declared in `criterion_texts` or assigned in those checks, count all its assigned checks across every step. A check is an exit-code check exactly when `target` is `result` and `path` is `/exit_code` or `/exitCode`. A criterion is exit-code-only exactly when it has at least one assigned check and all its assigned checks are exit-code checks. Another criterion's checks do not affect it. Mixed checks and zero checks are never exit-code-only. This is structural, independent of criterion wording, expected values, execution state and whether checks passed; no output-intent heuristic, lint warning, refusal or verdict change is introduced.

JSON rows expose `criterion_coverage`: an ordered array of `{criterion_id, check_count, exit_code_only}` (declared criterion order, then previously unseen assigned identities in step/check order). `check_count` is the authored number, not an executed/pass count. If authored `steps` are unavailable, expose null, meaning unknown; never infer coverage from server verdicts or prose. An explicit empty steps array with a declared criterion yields zero and false. Text shows one line per known criterion, `criterion ID: TEXT`, appending ` — checked by exit code only` only for true coverage; for example `criterion AC2: The command exits successfully. — checked by exit code only`. Use its authored text when available; otherwise retain the identity without inventing text. Print these facts for passed and failed results alike, including saved/read results. Missing authored coverage has no annotation and remains unknown in JSON. Existing summary, warnings, exit status and accounting rules remain unchanged. Neither the annotation nor a passed exit code claims that output was checked.

## Reused Story rows

A reused test keeps `state:passed` and has `cached:true`, `passed_at` (the prior
confirmed pass ISO timestamp), `calls:0`, `input_tokens:0`, `cached_input_tokens:0`, `output_tokens:0`, `cached_input_share:null`, `seconds:0`, `request_id:null` and
`report_url:null`. This is prior evidence, never a fresh runtime pass or fabricated provider cache share. Preserve
these fields in JSON. Render its result as `unchanged, passed HH:MM` when its
pass falls on today's local calendar date; otherwise use `unchanged, passed
YYYY-MM-DD`. Append `; force with pdd test --cache-clear <same Story selector>` to the table Result cell. Use that row's Story selector, shell-quoted when needed so the command selects the same Story. Use the injected current clock for date comparisons. Summaries
include `N Stories skipped` (singular `1 Story skipped`), counting Story identities
once even with sibling rows, and zero current calls for reused work. Mixed rows
retain ordinary failure/unknown exit precedence and current-call accounting.
A last-failed selection with valid history and no failures prints a plain no-failed-
Stories message, zero calls, empty JSON rows and exit 0, with no invented verdict.

For an executed test with a cache guard reason, retain `cache_reason` as a string in its JSON row and show it in the text Result cell alongside the actual outcome. Eligibility and reason wording belong to [the runtime client](runtime-client.prompt.md#declarations-that-require-a-run). Such rows are not cached, report real current calls, retain actual request/report identity, and participate in normal summaries and exit precedence. A provisional skip subsequently executed because of a changed interpreter identity appears only once as an executed row. Saved batch and UUID recovery retain the answer's `engine_sha` and `requested_model` so completed reads use the same identity rules as immediate results.

## Exit code

Exit codes are supplied by callers over [runtime outcome](runtime-outcome.prompt.md#progress-and-exit) through their state-to-exit mapping; this module owns no state-to-exit mapping.

2. The table: `Story`, `Test`, `Result`, `Checks`, `Time`. Story = the story title. Result is the [outcome text](runtime-outcome.prompt.md#progress-and-exit) (`not run`, `queued · 2 ahead`, or `running · step 3 of 5 · 4 AI calls so far` with server progress); a draft row adds ` (DRAFT)` to its result and to its report link line. Checks `n/m` or `-`. Time `21.0 s` or `-`.
3. One paste line per Story ([Prompt tests line](#prompt-tests-line)), in table order: `Prompt tests (<story>): ✓ 3 of 3 criteria · 10/10 checks · 1 AI call`, with ` (DRAFT)` after the story when a row of it ran a draft prompt; a Story with two test files gets one line for both. With one Story, its line is the only Prompt tests line (round-2 tester: no second line that repeats it). With two or more Stories, the overall summary line comes last of these lines, one line that an agent can paste into a PR: `Prompt tests: ✓ 3 of 3 criteria · 10/10 checks · 1 AI call`; `Prompt tests (DRAFT): …` when a row ran a draft prompt. A passed row without that list proves the job passed but not which criteria: never count its criteria as passed or failed. When every row of a line is such a row, the criteria part reads `passed · criteria details not reported` (`Prompt tests (one): ✓ passed · criteria details not reported · 2/2 checks · 1 AI call`); when only some are, the counted criteria of the other rows are followed by `· criteria details not reported`. Rows that are refused, not run, unknown, queued or running add `· N refused` (and so on). Calls count only ended rows; others add ` + N unknown`.

With neither field, preserve the existing block. A server next step suppresses conflicting client retry/fix advice, including refusal Fix/hint instructions and the AI-service/provider "run again" lines; keep refusal codes, causes, locations, reports and IDs.
   Existing fallback blocks:
   - `FAILED  <title> (<test>)` for every row whose state is `failed` or that has failed checks (`failed_checks.length > 0`), one line for each failed check `  AC1  step place-order  result /totalCents  expected 899, got 900` (or the check line `  AC1  step place-order  result /stdout` and its block), followed by a `Criterion: …` line when the authored criterion is at most 160 characters, the row warnings (for `failed` rows; non-`failed` rows keep their warnings in the existing bottom list), and then the report link. ## Summary mark and mixed exits

Apply this precedence to every summary: any failed row or any row with failed checks (`failedCheckCount(row) > 0`) → `✗`; otherwise a nonempty set of all passed rows → `✓`; otherwise any open (`queued`, `running` or `sent`) row → `running ·`; otherwise a set containing at least one actual busy row and consisting only of passed or actual busy rows → `busy ·`; otherwise → `no verdict ·`. An actual busy row has `busy:true` and state `not_run` or `not run`; stale busy flags on other states never make them busy. `busy:true` affects this summary mark and the JSON `busy` boolean only; `resultOutcome(row)` still decides the row's reason code (`no-server-verdict` on a bare `not run` + `busy:true` row without `retryable:true`, `busy_display` or a supplied busy note/reason). Empty rows have no verdict. Running mixed with refused remains running; passed mixed with actual busy remains busy. Keep counts, draft marks, calls and ordering.

Exit precedence is unchanged. Only when a failed row (or a row with failed checks, `failedCheckCount(row) > 0`) and an actual inconclusive row are both present and the batch exits 3, 4 or 5, print one notice after the summaries. An exit-3 flag such as interruption or lint uncertainty with only passed/failed rows does not authorize a no-verdict claim. Count distinct Story identities with a failed row or failed checks (`failedCheckCount(row) > 0`), and distinct Story identities with an inconclusive row contributing to the higher-priority exit: refused, not-run (including busy), unknown, queued, running or another nonterminal state. Multiple rows of one Story count once in each applicable set, and a single inconclusive row with failed checks belongs to both sets for its Story.

When an inconclusive Story is outside the failed set, use the brief's ordinary wording: `1 Story failed its checks. Another Story has no verdict, so the exit code is E.` For plural counts substitute `N Stories failed their checks` and `M other Stories have no verdict`; retain `Another Story has no verdict` when exactly one qualifying Story is outside the failed set. Count these other Stories once; an overlap with a failed Story does not increase the other-Story count. When there is no other inconclusive Story, use the truthful overlap wording: `1 Story failed its checks. That Story also has checks with no verdict, so the exit code is E.` For multiple failed Stories use `N Stories failed their checks. M of those Stories also have checks with no verdict, so the exit code is E.`; if M is one, use `1 of those Stories also has checks with no verdict`. E is the actual batch exit. Busy and open rows can cause this notice even though their summary mark remains busy or running; notice eligibility is separate from mark precedence.

## Prompt tests line

The paste lines above and every `summary_line` start with `ports.promptTestsLabel` (defaulting to `'Prompt tests'` for standalone `renderJson` vector entry compatibility): `<label> (<story>): …` for a Story and `<label>: …` for the total. Host callers supply the canonical paste-line label through `ports.promptTestsLabel`.

Each line is these parts, joined with ` · `, in this order: the label (with ` (<story>)` and then ` (DRAFT)` when a row ran a draft prompt; `<story>` is the row's `story` value, the Story file name without `.md` and with its case unchanged, never the Story title), a colon, the mark (`✓`, `✗`, `running ·`, `busy ·` or `no verdict ·`) and `<passed> of <total> criteria` (or the not-reported form in Text item 3); `<passed>/<total> checks`; `<F> failed` when non-`failed` rows contain `F > 0` failed checks (`failedCheckCount(row)` summed over rows whose state is not `failed`, placed immediately after `<passed>/<total> checks` and before non-pass outcome counts); optional broken-test (`N tests could not run`) and unchecked-criteria (`N criteria not checked; the Story is not a full pass`) counts; one [progress fragment](runtime-outcome.prompt.md#progress-and-exit) for open (`running` or `sent`) rows with server progress; `<N> <outcome>` for each distinct non-passed row's [outcome text](runtime-outcome.prompt.md#progress-and-exit) (`<state> (<reason.code>)`, omitting `progress` and `ahead`) in first-seen row order (for example `1 failed (check-failed)` or `1 refused (admission-refused)` or `1 not run (no-server-verdict)`); optional skipped-Story count; and last the AI calls. The AI calls count only sent rows (`row.phase === "server" || Boolean(row.request_id) || row.state === "sent"`) without server progress: ended sent rows with numeric `calls` add `row.calls`, ended sent rows without numeric `calls` add `row.known_calls ?? 0` (`1 AI call`, `N AI calls`, with ` (R for reruns)` when reruns used calls), and ` + U unknown` is appended only when at least one counted sent row is open (`queued`, `running`, `sent`) or lacks numeric `calls` (each such row adds `row.unknown_calls || 1`). Non-sent rows add `0` calls and `0` unknown. A running/sent row with server progress reports its calls in the progress fragment, so the AI calls part counts only the other rows and is omitted when none of them is a sent row. Example: `Prompt tests (one): no verdict · 0 of 0 criteria · 0/0 checks · 1 refused (admission-refused) · 0 AI calls`.

## JSON (stdout, `--json`)

One object: `{batch, repo, exit_code, summary_line, draft, token_usage, rows: [{story, title, test, state, checks, criteria, failed_checks, refusals, calls, input_tokens, cached_input_tokens, output_tokens, cached_input_share, seconds, requested_model, report_url, request_id, draft, reason, why, who, next_step, rerun, summary_line}], warnings}`. `token_usage` is `{input_tokens, cached_input_tokens, output_tokens, cached_input_share, complete}`, summing each token counter across all rows when every row has a numeric value for that counter (otherwise `'unknown'`), with `complete` true when `input_tokens` and `cached_input_tokens` are numeric across the batch (empty or all-cached batches sum to `0` with `cached_input_share: null` and `complete: true`). Failed checks carry `diagnosis`, including any check rerun data; failed rows carry the first failed check's diagnosis when the run-level fields are empty, plus failed-state `who`. Preserve supplied `why` and `next_step` for failed, refused, not-run and unknown states. Refusals retain their `cause`. `reason` is `{code, message}` from `resultOutcome` for every non-passed row (`null` only for `passed`). Preserve report-level `rerun` for the applicable state, otherwise null. `usage.calls` is the total including rerun calls; `rerun.calls` is the rerun share, shown in the Prompt tests line as `(N for reruns)`. When usage is missing on a sent row, omit the unknown total rather than printing zero. Top-level `summary_line` in `renderJson` always uses the overall unprefixed `Prompt tests:` label (`story = null`), even when `rows` has only one Story; each row's `summary_line` is the paste line of its Story (`Prompt tests (<story>): …`). `draft` is true for a row that ran a draft prompt, and at the top when any row did. ## Progress and causes
Every pdd command reports progress and errors through these two helpers, so all progress has one style.
- Export `progressTicker(stream, now, everyMs = 15000)`. A slow step (more than about 2 s: network, lint, upload, the queue, AI calls, git, gh, Herdr, an agent) first prints one plain line that ends with `…`, for example `Checking 3 files (29 KB) on the PDD interpreter (lint, 0 AI calls)…`. The returned `tick(text)` prints `<text> · <time>` at most once every `everyMs`, counted from the start, with the time from `sinceText` (`N s` under a minute, else `N min`). Each step ends with a clear line: the result, or `Try ready: <link>`.
- Progress goes to stderr only, never to stdout, so the result and `--json` stay clean. A person and an agent (no terminal) get the same lines: no spinner, no carriage return, no colour codes.
- Export `causeText(value, secrets = [])`: the first nonempty line of a tool's or server's error text, with control characters, the given secrets and GitHub or API tokens removed, at most 300 characters. An error line says what failed, this real reason, and what to do next.

## Step time limits

Export `stepTimeLimit(answer, {steps=[], secrets=[]}={})` to recognize a server step time refusal from raw report/sample/step refusals. The published server currently reports legacy `graph-provider-failure` with explicit timeout/timed-out/time-limit detail (including failure_cause.detail or legacy failure_cause.kind timeout); do not classify a generic provider failure, queue wait or client polling deadline as a step limit. A typed failure_cause.kind `step_timeout` also identifies a step limit independent of its code. No dedicated new code is assumed until the runtime publishes it.

Identify the step by its reported step_id/name, otherwise a valid steps[N] refusal section mapped to authored step IDs (including the sole matching companion refusal section when raw sample metadata omits it), otherwise say unnamed step. Preserve/sanitize the server-provided name. Use an explicit positive timeout_seconds/limit_seconds from the refusal or its details, otherwise a timeout detail's explicit seconds/minutes; legacy default is180seconds. A typed step_timeout without a reported duration uses the requested600second policy. Never infer the time limit from total job elapsed time. Return code, step, minutes and the message `Step NAME took more than N minutes and was stopped.` plus `Make the step smaller, for example split 30 moves into 3 steps of 10.`

This is inconclusive execution, never a failed expectation. Project it as unknown with structured time_limit and reason, retaining actual usage, earlier check evidence and report/ID. In text, give a STOPPED block with that step message and advice, suppress the generic provider-failure/failed-expectation framing for this refusal. Other provider failures retain existing behavior. JSON contains the same message and structured time_limit. No automatic retry is authorized.
