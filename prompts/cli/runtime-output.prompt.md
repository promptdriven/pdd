# Runtime output

Own `src/runtime-output.mjs`. It turns `pdd test` rows into the terminal table, the `--json` object and the exit code. It makes no call and writes no file.

## Incomplete selected tests and criteria

Rows can carry `unsent:true` and `not_checked:[{criterion_id,text,reason}]` from local validation. JSON retains both. List locally broken unsent rows first as `not run (broken-test)` in text and JSON, with their file, reason and fix hint before other results. Count them in each applicable summary as `N tests could not run`. Preserve other summary and exit precedence rules.

For each not-checked criterion print `ID: not checked: <reason>` and its text. It is never a passed criterion. Keep its place in the full Story total, exclude its ID from reported passed counts, and retain other checked results and real usage. A run with any such criterion is not a full Story pass; say so in text and summaries. A server pass becomes `not_run` at the client boundary; failures and other inconclusive states retain their existing meaning. Saved reads render the same facts.

## Rows

Preserve an optional `path` on each local shared-reader refusal in `jsonRow`.
It names the affected repository-relative prompt, including a called prompt.
Omit it when absent; keep all existing refusal fields and cleaning rules.

A row is one test: `story`, `title`, `test`, `state`, `checks {passed, total}`, `failed_checks [{criterion_id, step_id, criterion_text, target, path, expected, actual, diagnosis}]`, `refusals [{code, field, section, message, engine_message, hint, reason, fix, where, cause}]`, `calls`, `seconds`, `requested_model`, `report_url`, `request_id`, diagnosis fields `why`, `who`, `next_step`, and the outcome fields `progress` and `ahead` when the server supplied them. When usage accounting is known, JSON may also include `known_calls`, `unknown_calls` and `accounting_complete`. A complete receipt keeps its numeric `usage.calls` total even when `known_calls` is lower. Incomplete multi-ID usage keeps `calls` unknown and reports the summed known lower bound and unknown count. A confirmed unstarted capacity row has `busy:true`, `can_retry:true` and state `not_run`; it is not a source refusal or failed assertion. Render its capacity advice without a Fix-the-test line and mark a summary containing only passed rows and actual busy rows (with at least one busy row) `busy`, not ✗. Mixed actual failures retain ✗. Preserve request ID, report and zero-call accounting. States: `passed`, `failed`, `refused`, `not_run`, `unknown`, `queued`, `running`.

- From a server answer: checks come from `result.report.samples[0].steps[].checks[]`; refusals from `result.refusals` (prompt-runtime #379 adds `reason` in plain words, `fix`, `file`, `at`, `where` = file and place as one text, and `cause`: `call-budget`, `ai-service`, `test`, `prompt`, `server` or `unknown`; `where` falls back to `file` and `at`; each is null when missing); calls from `usage.calls`; the model from `usage.requested_model` (else the report's `evaluation.requested_model`). pdd uses the canonical selected outcome, not the server's display `outcome` string.
- Incomplete accounting (`accounting_complete:false` on any supplied surface, conflicting or malformed counters/flags, known calls above the reported total, or positive `unknown_calls`) never projects a complete numeric row call total, even when a calls counter is numeric. Preserve the known lower bound in summary totals and append the unknown part, for example `2 AI calls + 1 unknown`; absent unknown-count detail still contributes an unknown component. Keep row `calls` unknown, expose JSON `known_calls`, `unknown_calls`, `accounting_complete:false`, and retain the existing public summary format. Pending or unavailable usage remains unknown; only positively unsent work defaults to zero. Across restart/capacity IDs, sum each ID's known and unknown components; a later complete replacement cannot erase earlier incomplete usage or its raw receipt.
- Seconds are rounded to 0.1.
- Expected and got values that fit on one line print as JSON on the check line, so strings are quoted and escaped (`"Sam\n"` differs from `"Sam"`). They fit when no string has a line break before its end and each JSON is at most 80 characters.
- Other values (round-2 tester: a CLI's stdout lost its line breaks and was cut near the difference) print as a block under the check line: `    expected:` and `    got:`, each followed by its lines, 6 spaces in. A string shows its own lines with no quotes, and `(ends with a line break)` when it ends with one; any other value shows as JSON with 2-space indents. pdd never cuts inside a line. A value shows at most 20 lines: from line 1, or from 2 lines before the first line where two strings differ when that line is later. Lines left out are named: `… N lines before` above, `… N more lines in the report` below. Each line loses control characters and the token but keeps its spaces.
- Clean all server text: remove control characters, the token and server paths (`/home/…`, `/srv/…`, `/var/…`, `/tmp/…` and similar). Expected and actual values keep their JSON type but lose the token.

## Compatibility projection

The existing module function `projectAnswer(answer, options)` accepts optional
`sourceFiles` and forwards that actual captured manifest to `outcomeFor`.
Project its `compatibility` facts and the client's separately labelled
`client_advice` without reclassifying server rows or admission. Native text/JSON
rows retain these fields for immediate and saved lint results. Standalone lint
formatting remains client-owned. Apply the existing recursive text/secret/path
cleaning to all compatibility strings while keeping digests, identity order,
nulls, Booleans and counts typed. No arbitrary wire fields, fixture bodies or
server host paths enter the view. A report's zero preflight calls never overrides
unknown paid usage. The existing minimal `renderJson` Runtime entry below does
not bind `projectAnswer`, transport, captured-source association or these native
compatibility rows; those cases require the native public boundaries.

## Criterion check facts

The existing module functions `renderJson(options)` and `renderText(options)` use each row's authored `steps[].checks` and `criterion_texts`, already retained for immediate and saved/read results. For each criterion identity declared in `criterion_texts` or assigned in those checks, count all its assigned checks across every step. A check is an exit-code check exactly when `target` is `result` and `path` is `/exit_code` or `/exitCode`. A criterion is exit-code-only exactly when it has at least one assigned check and all its assigned checks are exit-code checks. Another criterion's checks do not affect it. Mixed checks and zero checks are never exit-code-only. This is structural, independent of criterion wording, expected values, execution state and whether checks passed; no output-intent heuristic, lint warning, refusal or verdict change is introduced.

JSON rows expose `criterion_coverage`: an ordered array of `{criterion_id, check_count, exit_code_only}` (declared criterion order, then previously unseen assigned identities in step/check order). `check_count` is the authored number, not an executed/pass count. If authored `steps` are unavailable, expose null, meaning unknown; never infer coverage from server verdicts or prose. An explicit empty steps array with a declared criterion yields zero and false. Text shows one line per known criterion, `criterion ID: TEXT`, appending ` — checked by exit code only` only for true coverage; for example `criterion AC2: The command exits successfully. — checked by exit code only`. Use its authored text when available; otherwise retain the identity without inventing text. Print these facts for passed and failed results alike, including saved/read results. Missing authored coverage has no annotation and remains unknown in JSON. Existing summary, warnings, exit status and accounting rules remain unchanged. Neither the annotation nor a passed exit code claims that output was checked.

## Reused Story rows

A reused test keeps `state:passed` and has `cached:true`, `passed_at` (the prior
confirmed pass ISO timestamp), `calls:0`, `seconds:0`, `request_id:null` and
`report_url:null`. This is prior evidence, never a fresh runtime pass. Preserve
these fields in JSON. Render its result as `unchanged, passed HH:MM` when its
pass falls on today's local calendar date; otherwise use `unchanged, passed
YYYY-MM-DD`. Append `; force with pdd test --cache-clear <same Story selector>` to the table Result cell. Use that row's Story selector, shell-quoted when needed so the command selects the same Story. Use the injected current clock for date comparisons. Summaries
include `N Stories skipped` (singular `1 Story skipped`), counting Story identities
once even with sibling rows, and zero current calls for reused work. Mixed rows
retain ordinary failure/unknown exit precedence and current-call accounting.
A last-failed selection with valid history and no failures prints a plain no-failed-
Stories message, zero calls, empty JSON rows and exit 0, with no invented verdict.

For an executed test with a cache guard reason, retain `cache_reason` as a string in its JSON row and show it in the text Result cell alongside the actual outcome. Eligibility and reason wording belong to [the runtime client](runtime-client.prompt.md#declarations-that-require-a-run). Such rows are not cached, report real current calls, retain actual request/report identity, and participate in normal summaries and exit precedence. A provisional skip subsequently executed because of a changed interpreter identity appears only once as an executed row. Saved batch and UUID recovery retain the answer's `engine_sha` and `requested_model` so completed reads use the same identity rules as immediate results.

## Exit code

Use the shared [outcome exit policy](runtime-outcome.prompt.md#progress-and-exit). No independent state-to-exit mapping.

2. The table: `Story`, `Test`, `Result`, `Checks`, `Time`. Story = the story title. Result is the [outcome text](runtime-outcome.prompt.md#progress-and-exit) (`not run`, `queued · 2 ahead`, or `running · step 3 of 5 · 4 AI calls so far` with server progress); a draft row adds ` (DRAFT)` to its result and to its report link line. Checks `n/m` or `-`. Time `21.0 s` or `-`.
3. One paste line per Story ([Prompt tests line](#prompt-tests-line)), in table order: `Prompt tests (<story>): ✓ 3 of 3 criteria · 10/10 checks · 1 AI call`, with ` (DRAFT)` after the story when a row of it ran a draft prompt; a Story with two test files gets one line for both. With one Story, its line is the only Prompt tests line (round-2 tester: no second line that repeats it). With two or more Stories, the overall summary line comes last of these lines, one line that an agent can paste into a PR: `Prompt tests: ✓ 3 of 3 criteria · 10/10 checks · 1 AI call`; `Prompt tests (DRAFT): …` when a row ran a draft prompt. Use the summary mark rule below for both Story and overall lines. Criteria come from the report's `criterion_results`; a row that is not `passed` and has no such list counts its test's criteria (`criteria_total`, or `0` when absent), with `0` passed. A passed row without that list proves the job passed but not which criteria: never count its criteria as passed or failed. When every row of a line is such a row, the criteria part reads `passed · criteria details not reported` (`Prompt tests (one): ✓ passed · criteria details not reported · 2/2 checks · 1 AI call`); when only some are, the counted criteria of the other rows are followed by `· criteria details not reported`. Rows that are refused, not run, unknown, queued or running add `· N refused` (and so on). Calls count only ended rows; others add ` + N unknown`.
4. A block for each problem row, failed rows first. Except for the [busy-check display](#busy-check-display), for refused, not-run and unknown rows, show each supplied nonempty server `why` as `Why:` and `next_step` as `Next:`, using the existing text cleaning. The client supplies accepted server advice under its no-verdict explanation rule; client-generated transport reasons remain valid fallback explanations. Each field overrides only its corresponding fallback: why-only keeps existing next-step advice; next-step-only keeps the existing explanation and removes only a conflicting retry sentence. For NOT RUN, preserve the true busy explanation when a request was sent; never claim it was unsent, remove the whole explanation, or leave a dangling colon when advice replaces it. With neither field, preserve the existing block. A server next step suppresses conflicting client retry/fix advice, including refusal Fix/hint instructions and the AI-service/provider "run again" lines; keep refusal codes, causes, locations, reports and IDs.
   Existing fallback blocks:
   - `FAILED  <title> (<test>)`, one line for each failed check `  AC1  step place-order  result /totalCents  expected 899, got 900` (or the check line `  AC1  step place-order  result /stdout` and its block), followed by a `Criterion: …` line when the authored criterion is at most 160 characters, the row warnings, and then the report link. For target `error`, say `got no error (a normal result)` only when the step has a result and no error, or diagnosis kind `no-error`/`needs-tool`; otherwise keep `{"missing":true}`. Print each failed check's own `Why:` and `Next:` pair from its diagnosis. With no diagnosis, use the failed row's run-level fields when both are present; otherwise say `Next: show this check to the person. A person decides expected values. The agent may propose a change, and never makes it.` For a failed step with rerun diagnosis or a matching report rerun, print one `Rerun:` line under its first failed check; `Rerun: failed N of M (stable). A recheck of the same files will not help.` or `Rerun: failed N of M (unstable). Make the rule in the prompt firmer.`; `failed 0` is `passed M of M reruns.` and `runs: 1` prints no verdict. Rerun lines carry no call count; rerun calls appear only in the summary line as `(N for reruns)`. A skipped rerun says `Rerun: skipped (<reason>).`
   - `REFUSED before sending (not sent, 0 AI calls)`, then for each row `  <test>  step N  <code>` and the message and hint lines.
   - `REFUSED  <title> (<test>)`, then for each refusal with a `reason`: `  <code>: <reason>`, `  Where: <where>` when there is one, and `  Fix: <fix>`; when `cause` is `ai-service` the last line is `  Your test is fine. Run it again.` in place of the fix. A refusal with no `reason` (the live server before #379) keeps `  <code>  <section>  <message>` and the engine message when it adds detail. Both end with the `pdd:` hint when there is one.
   - `NOT RUN  <title> (<test>): <message> (<code>)`.
   - `STILL RUNNING after <limit>: <title>. Do not send it again.` at the time limit; the limit is `90 s` for the agent default, else `N min` (after Ctrl-C: `STILL RUNNING when pdd stopped reading: …`; in `--read`, or with no known limit: `STILL RUNNING: …`)
   - `UNKNOWN  <title>: the run may have executed. Its result is unknown.` and the server's reason.
   - An AI provider failure (state `unknown` with `graph-provider-failure`, or a sample `failure_cause.kind` of `transport_unknown`) has its own block: `UNKNOWN  <title>: the AI provider failed during the run. It is not a failed check. Do not send it again yet.`, then the code, the cause and the report link. The block ends with `To try again, run \`pdd test\` again (a new request).` pdd never resends it.

5. With `--details`: every check of each row, failed checks first.
6. `X of Y stories passed. Model asked for: M.` Skip the model part when it is not known. Time is shown only for ended rows.

## Summary mark and mixed exits

Apply this precedence to every summary: any failed row → `✗`; otherwise a nonempty set of all passed rows → `✓`; otherwise any queued/running row → `running ·`; otherwise any refused, unknown, or nonbusy not-run row → `no verdict ·`; otherwise a set containing at least one actual busy row and consisting only of passed or actual busy rows → `busy ·`; otherwise → `no verdict ·`. An actual busy row has state `not_run` and `busy:true`; stale busy flags on other states never make them busy. Empty rows have no verdict. Running mixed with refused remains running; passed mixed with actual busy remains busy. Keep counts, draft marks, calls and ordering.

Exit precedence is unchanged. Only when a failed row and an actual inconclusive row are both present and the batch exits 3, 4 or 5, print one notice after the summaries. An exit-3 flag such as interruption or lint uncertainty with only passed/failed rows does not authorize a no-verdict claim. Count distinct Story identities with a failed row, and distinct Story identities with an inconclusive row contributing to the higher-priority exit: refused, not-run (including busy), unknown, queued, running or another nonterminal state. Multiple rows of one Story count once in each applicable set.

When an inconclusive Story is outside the failed set, use the brief's ordinary wording: `1 Story failed its checks. Another Story has no verdict, so the exit code is E.` For plural counts substitute `N Stories failed their checks` and `M other Stories have no verdict`; retain `Another Story has no verdict` when exactly one qualifying Story is outside the failed set. Count these other Stories once; an overlap with a failed Story does not increase the other-Story count. When there is no other inconclusive Story, use the truthful overlap wording: `1 Story failed its checks. That Story also has checks with no verdict, so the exit code is E.` For multiple failed Stories use `N Stories failed their checks. M of those Stories also have checks with no verdict, so the exit code is E.`; if M is one, use `1 of those Stories also has checks with no verdict`. E is the actual batch exit. Busy and open rows can cause this notice even though their summary mark remains busy or running; notice eligibility is separate from mark precedence.

## Prompt tests line

The paste lines above and every `summary_line` start with the label `Prompt tests`: `Prompt tests (<story>): …` for a Story and `Prompt tests: …` for the total. pdd writes only this label. Export `PROMPT_TESTS_LABEL` (`'Prompt tests'`) and `PROMPT_TESTS_WORDS`, the regular-expression source `(?:Prompt tests|Runtime check)`. Every reader of these lines ([workflow runner](workflow-runner.prompt.md#prompt-tests-lines) and [read-only review](workflow-view.prompt.md)) finds them with that pattern, so the `Runtime check (<story>): …` lines of older PR bodies, saved run summaries and saved `--json` results read the same way. Forbidden: a new line that says `Runtime check`, or an old `Runtime check` line that a reader skips.

Each line is these parts, joined with ` · `, in this order: the label (with ` (<story>)` and then ` (DRAFT)` when a row ran a draft prompt; `<story>` is the row's `story` value, the Story file name without `.md` and with its case unchanged, never the Story title), a colon, the mark (`✓`, `✗`, `running ·`, `busy ·` or `no verdict ·`) and `<passed> of <total> criteria` (or the not-reported form in Text item 3); `<passed>/<total> checks`; one [progress fragment](runtime-outcome.prompt.md#progress-and-exit) for the running rows with server progress; one count for each of refused, not run, unknown, queued and running that is above zero, in that order (for example `1 refused`); and last the AI calls. The AI calls count only rows that reached the server (`phase` is `server`): the sum of their known calls (`1 AI call`, `N AI calls`, with ` (R for reruns)` when reruns used calls), then ` + U unknown` only when some of those rows have no known call count (U adds each such row's `unknown_calls`, at least 1). A row that pdd refused before sending adds no call and no unknown. A running row with server progress reports its calls in the progress fragment, so the AI calls part counts only the other rows, and it is left out when none of them reached the server. Example: `Prompt tests (one): no verdict · 0 of 0 criteria · 0/0 checks · 1 refused · 0 AI calls`.

## JSON (stdout, `--json`)

One object: `{batch, repo, exit_code, summary_line, draft, rows: [{story, title, test, state, checks, criteria, failed_checks, refusals, calls, seconds, requested_model, report_url, request_id, draft, reason, why, who, next_step, rerun, summary_line}], warnings}`. Failed checks carry `diagnosis`, including any check rerun data; failed rows carry the first failed check's diagnosis when the run-level fields are empty, plus failed-state `who`. Preserve supplied `why` and `next_step` for failed, refused, not-run and unknown states. Refusals retain their `cause`. `reason` is `{code, message}` for a row that was not run or is unknown (`graph-provider-failure` for a provider failure), else null; passed and failed rows keep `reason` null. Preserve report-level `rerun` for the applicable state, otherwise null. `usage.calls` is the total including rerun calls; `rerun.calls` is the rerun share, shown in the Prompt tests line as `(N for reruns)`. When usage is missing, omit the unknown total rather than printing zero. A row's `summary_line` is the paste line of its Story. `draft` is true for a row that ran a draft prompt, and at the top when any row did. When the server answer has `draft_prompts` (a list of repo paths), a nonempty list means DRAFT and an empty one means not DRAFT; it wins over pdd's local guess. Older servers without the field keep the local guess. Nothing else goes to stdout.

`progress`, `ahead` and, for a retryable refusal before dispatch, its server code and text as
the row `note`. The table result, the text blocks, JSON, the Prompt tests lines and the
exit code read that state. The summary mark (✓, ✗, running, busy, no verdict)
stays the display rule above. A
retryable refusal before dispatch (any code) is `not run`, exit 5, with the server's text retained in JSON and the [plain busy display](#busy-check-display) in text,
without a cross or refusal block. JSON rows keep supplied `progress` and `ahead`
and each refusal's `field`; missing progress fields stay missing, never zero.

## Busy check display

For a retryable Check refusal with dispatch `not_started`, render its terminal not-run block as exactly `Not run: PDD stayed busy for <duration>, so your check did not start. Nothing was charged. Try again in a few minutes: pdd test <story>`. This text takes precedence over raw refusal codes, messages, Why/Next and source-repair advice. Before that line, also print the projected reason message when its code is timeout-flag, deadline or interrupted, so capacity advice cannot hide the caller's stop cause or the --timeout flag. Retain reports and request identities. For a result containing only passed rows and retryable busy rows, keep the complete coverage counts but label the prompt coverage line Runtime coverage, so the busy response uses the same plain service vocabulary. Other coverage labels keep their existing rules. Preserve classification, exit 5, usage, raw receipts and every existing technical JSON field, including reason, refusals and server advice; display cleanup must not replace their values.

Read duration only from the selected retryable refusal's `max_wait_seconds` (the supplied server contract says the deadline was the actual wait). A valid value is a positive safe integer. When divisible by 60, format whole minutes; otherwise format seconds, with singular units for 1 (`600` → `10 minutes`, `60` → `1 minute`, `90` → `90 seconds`, `1` → `1 second`). Missing or invalid duration omits ` for <duration>` entirely. Never infer it from usage, retry delay or local clocks.

Use that row's real Story selector, shell-quoted as needed. Missing, blank or `-` Story uses the same timed or untimed sentence ending with `Try again in a few minutes.` and no command. Confirmed unstarted capacity rows use the same plain fallback when no duration is available; locally held unsent rows keep their unsent explanation. Interruption's `Stopped.` explanation takes precedence. None of these selected busy messages may expose interpreter, slot, pool, model, login or account. Keep text-only busy metadata internal; do not add public JSON fields for rendering.

## Try usage
Export tryUsage(answer, {cap}={}), tryUsageLine(usage, {command=false}={}) and tryUsageHeaders(usage). Normalize only nonnegative safe-integer counts; absent/malformed counts are unknown, never invented zero. Owner model calls.cap/remaining, session.max_calls/remaining_calls and call usage.calls/report.remaining_calls are the existing server fields. Derive cumulative used only from valid cap and remaining <=cap; this is the Try session allowance, not a machine/account/tester allowance. ## Progress and causes
Every pdd command reports progress and errors through these two helpers, so all progress has one style.
- Export `progressTicker(stream, now, everyMs = 15000)`. A slow step (more than about 2 s: network, lint, upload, the queue, AI calls, git, gh, Herdr, an agent) first prints one plain line that ends with `…`, for example `Checking 3 files (29 KB) on the PDD interpreter (lint, 0 AI calls)…`. The returned `tick(text)` prints `<text> · <time>` at most once every `everyMs`, counted from the start, with the time from `sinceText` (`N s` under a minute, else `N min`). Each step ends with a clear line: the result, or `Try ready: <link>`.
- Progress goes to stderr only, never to stdout, so the result and `--json` stay clean. A person and an agent (no terminal) get the same lines: no spinner, no carriage return, no colour codes.
- Export `causeText(value, secrets = [])`: the first nonempty line of a tool's or server's error text, with control characters, the given secrets and GitHub or API tokens removed, at most 300 characters. An error line says what failed, this real reason, and what to do next.

## Step time limits

Export `stepTimeLimit(answer, {steps=[], secrets=[]}={})` to recognize a server step time refusal from raw report/sample/step refusals. The published server currently reports legacy `graph-provider-failure` with explicit timeout/timed-out/time-limit detail (including failure_cause.detail or legacy failure_cause.kind timeout); do not classify a generic provider failure, queue wait or client polling deadline as a step limit. A typed failure_cause.kind `step_timeout` also identifies a step limit independent of its code. No dedicated new code is assumed until the runtime publishes it.

Identify the step by its reported step_id/name, otherwise a valid steps[N] refusal section mapped to authored step IDs (including the sole matching companion refusal section when raw sample metadata omits it), otherwise say unnamed step. Preserve/sanitize the server-provided name. Use an explicit positive timeout_seconds/limit_seconds from the refusal or its details, otherwise a timeout detail's explicit seconds/minutes; legacy default is180seconds. A typed step_timeout without a reported duration uses the requested600second policy. Never infer the time limit from total job elapsed time. Return code, step, minutes and the message `Step NAME took more than N minutes and was stopped.` plus `Make the step smaller, for example split 30 moves into 3 steps of 10.`

This is inconclusive execution, never a failed expectation. Project it as unknown with structured time_limit and reason, retaining actual usage, earlier check evidence and report/ID. In text, give a STOPPED block with that step message and advice, suppress the generic provider-failure/failed-expectation framing for this refusal. Other provider failures retain existing behavior. JSON contains the same message and structured time_limit. No automatic retry is authorized.

## Module binding coverage

Check and lint results with supplied coverage print `N of M modules bound`, followed by each selected unbound module path, reason and attempted port. JSON includes `coverage: {available, bound, total, modules}` with each module's path, state and, when unbound, reason and port_attempt. Unknown inventory prints `Module binding coverage unavailable: no pdd-bindings.json.` and has available:false, bound:null, total:null, modules:[].
