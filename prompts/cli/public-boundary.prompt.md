# Local PDD command boundary

PDD supplies a guide and recipes for the user's existing coding-agent conversation. Keep `pdd` as the command name. Provide local discovery without hosted-service commands or private dependencies.

The local command surface includes help (root help, known local command help and the `help prompting` topic), `--version`, `workflow list [--json]`, `completion bash|zsh` and `setup`. There is no `session` command and no `workflow feature|bug|small-change` chat launcher: people open Codex or Claude as usual and call a PDD skill by name: `$pdd-feature` in Codex, `/pdd-feature` in Claude Code (also pdd-bug, pdd-small-change, pdd-prompting). Unknown or excluded commands, including with help flags, refuse clearly with exit2 before effects. Do not look up installed service adapters, forward arbitrary argv, import private dependencies, implement authentication, make PDD service calls, change accounts or install services. The read-only `workflow view ISSUE` route uses saved local records and local Git/file reads only, with no chat, approval or network effects. The workflow runner routes (run, done, approve, changes, cancel, status, open) may use ordinary authenticated Git/GitHub tools and Herdr through the distinct runner. Expose only supported local command declarations and validators.

Keep one catalog authoritative for help/parser/completion. Parse before local reads. Success returns0; unsupported syntax2; missing guidance/local filesystem failure1. Do not echo untrusted input. Local discovery reads do not create project files; only [project setup](project-setup.prompt.md) writes one, on request. Full-access launch modes are owned by [area chats](workflow-chat.prompt.md); no global permission rewrite is performed. On explicit setup consent, [agent MCP setup](agent-mcp-setup.prompt.md) may add only the previewed PDD server registration and its per-server approvals to detected agents’ user configurations. No hosted workflow service or fallback. Package metadata/lock must be dependency-free, retain bin `pdd`, include complete docs/skills/recipes/example and avoid lifecycle scripts. Source use and private temporary package-consumer tests are supported; registry publication/global installation are outside scope.

## Dependencies

Read the entire [Prompting guide](../../docs/prompting-guide.md) before authoring prompts or Stories. Source files implement these contracts; tests exercise observable behavior from the actual packed package.

pdd pastes no guide, skill or recipe text: help names the paths of the installed Prompting guide and RUNBOOK and gives a short summary ([Learn PDD](pdd-cli.prompt.md#learn-pdd)), and the agent loads the skills on demand.

The package ships five skills in `skills/` (pdd-prompting, pdd-setup, pdd-small-change, pdd-bug, pdd-feature). The standard installer (`npx skills add promptdriven/pdd`) finds exactly these: keep every other SKILL.md out of the repo's `skills/` folder. Only `pdd setup` installs them, through [skills install](skills-install.prompt.md), and only for an agent that cannot find them (for example after `npx skills add`, it copies nothing). It writes skills only to the agent's user folder (`~/.agents/skills/`, and `~/.claude/skills/` or `$CLAUDE_CONFIG_DIR/skills/`), never to the person's repo. Workflow runs work with no installed skills: the runner reads the package's `skills/` folder.

Workflow execution uses `pdd workflow run NAME ISSUE [--agent codex|claude] [--base BRANCH]` ([NAMES](command-catalog.prompt.md#names)) and the runner routes done, approve, changes, cancel, status and open. The [runner](workflow-runner.prompt.md) owns run records, area chats, person approval and real GitHub PR effects. The CLI parses and dispatches. No user-supplied native-argument passthrough, hosted engine or auth/provider gate.

The explicit local `workflow prove ISSUE --test COMMAND --expect TEXT` route may execute only the supplied proof command through [old-code proof](workflow-prove.prompt.md), which is required generation/runtime/verification context for this exception. Reading notes or replay evidence never executes supplied commands. Prove reads no gh token, calls no PDD interpreter and performs no publication or workflow approval.

## PDD interpreter

The PDD interpreter is the hosted service that checks and runs prompts. Every line that pdd writes itself for a person calls it "the PDD interpreter", or "the interpreter" after the first mention: help, errors, progress and status lines, PR text and the Try guide text. Forbidden: "PDD runtime" or "the runtime" for this service in such a line.

Machine-read words keep "runtime", because programs, saved files and people's typing depend on them: the schema ids `prompt-runtime.*`, the default host and `DEFAULT_RUNTIME_URL`, `PDD_RUNTIME_URL`, the state folder `~/.pdd/runtime`, `runtime-capture-v1`, the local dispositions `runtime-check` and `runtime-try`, the block label `Runtime interface` in a prompt file (also in messages that tell the person to add or fix that block), and the detection of the server's `The runtime opens soon.` and `The runtime refused this job…` texts. A server text that pdd prints as it got it stays unchanged. The summary line is `Prompt tests (<story>): …`; pdd still reads the older `Runtime check (<story>): …` lines of saved results and PR bodies ([Prompt tests line](runtime-output.prompt.md#prompt-tests-line)).

This is the one exception to the no-service rules above. The `test`, `lint` and `simulate` commands ([Names](command-catalog.prompt.md#names)) and the [Try MCP](try-mcp.prompt.md) tools served by `pdd mcp` call the PDD interpreter, with the user's gh token ([runtime client](runtime-client.prompt.md)). The token comes from `gh auth token` and stays in memory: never in files, logs, argv, URLs or error text. They send the repo's Git-visible files (with secret names refused) and keep run state outside the repo. No other command calls a hosted service or reads a token; MCP reads credentials only when a tool needs interpreter access. The interpreter address is one setting: `PDD_RUNTIME_URL`, else one default constant in the runtime client.

## Command words

Every line that pdd writes itself for a person names the commands with the [Names](command-catalog.prompt.md#names) words: `pdd test`, `pdd lint`, `pdd simulate` and `pdd workflow run`. This includes help, next-step hints, errors, progress and status lines, PR text, MCP tool texts and the Try guide text. A wrapper error of `pdd simulate --cli` or `--serve` starts with the neutral label `pdd:`. Forbidden in such a line: `pdd check`, `pdd try` or `pdd try:`. Only the [removal lines](argument-parser.prompt.md#removed-names) name `pdd check` and `pdd try`. Readers of text that older versions saved (batch notes, PR bodies, run summaries) accept the old words too.

Machine-read words keep `check` and `try`, because servers, saved files and scripts depend on them: the wire commands `check` and `try`, the `/v1/try/…` paths, the folder `.pdd/try`, the `PDD Try launcher v1` marker, the `x-pdd-try-*` headers, the saved `tries/` records, the local dispositions `runtime-check` and `runtime-try`, and the workflow step names `check` and `try`. A server text that pdd prints as it got it stays as the server sent it, even when it names an old command.

The package may include a licensed, attributed vendored public TOML parser under `src/vendor/` for safe config validation. It requires no npm install or registry access at runtime.
