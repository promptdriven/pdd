# Reproduced bug relation effects

## Reproduced bug relation boundary

Expose new native production function `applyReproducedBugRelations({cwd,repository,issue,relations}, ports)`; this is a required implementation, not an existing API. Use each relation from the [findings input](../../skills/pdd-bug/steps/findings.md), without changing its shape or agent-selected meaning. The caller binds input and durable dispatch checkpoints before invocation. Return `{outcomes}` in input order, with exactly `{index,status,reason}` per relation, with status `none`, `applied`, `already-present`, `held`, `failed`, or `unknown` and a stable nonblank diagnostic reason, empty only for `none` or `applied`. Reject malformed input before all effects. The caller persists the result and dispatch checkpoints. Never decide semantics from a quote or classification.

Before any batch mutation validate all quotes against the exact current trusted source and identified content revision through existing evidence locators and trust owner. Missing, empty, changed, inaccessible, unavailable, untrusted, unsafe or mismatched source holds the entire batch with zero writes. Recheck source revision, quote, authority, claim, endpoint state and ownership at each effect boundary and after waits. A matching quote establishes existence only. Reuse the dependency model for complete graph, self, duplicate, unknown, cycle and human removal checks and its blocked-by effect. Reuse sort's paced sub-issue transport and current claim and removal guards. The Class parent must be an explicit existing open `Class:` issue selected by the agent, distinct from a Global fix umbrella; do not discover or create it. Existing native links report already-present; human-removed links remain held. No closure or reassignment is allowed.

For a duplicate effect implement a native GitHub transport through the existing paced GitHub/comment ports: after live verification that the current actor has write access and the current claim permits the write, POST `/repos/{owner}/{repo}/issues/{duplicate}/comments` with exactly `Duplicate of #N`, where N is the explicit canonical issue in the same repository. Read the duplicate issue's GraphQL timeline connection through all pages, including `MarkedAsDuplicateEvent` and `UnmarkedAsDuplicateEvent`, selecting `id`, `createdAt`, `actor`, `canonical` and `duplicate` identities; require complete current observations and exact endpoints. Confirm the marking only from a matching event by the authorized actor after dispatch; a later matching unmark wins and prevents recreation. If the pre-read shows the selected current marking, report already-present; a confirmed human Undo holds it. Check identity, ordering and permissions afresh after waits. The documented [marking route](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/marking-issues-or-pull-requests-as-a-duplicate), [comment endpoint](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment) and [timeline event](https://docs.github.com/en/graphql/reference/issues#markedasduplicateevent) are design authorities, not evidence of live execution. If POST acknowledgement or readback is unknown, persist unknown, stop the batch and use read-only recovery; never resend. A failed mutation also stops the batch. Keep prior confirmed outcomes and report later proposals held.
