# PDD interpreter runbook

Fix both: the brakes (the real defect) and the warning light (a test or check that would catch it next time). Brakes first. If the agent cannot find the defect yet, it fixes the warning light first: it adds what makes the defect visible (a failing reproducer test, a precise error, logging), so the cause becomes easy to find, and then it fixes the brakes. A warning-light-only change must say 'Not fixed yet: this helps find the cause' on the PR, and the issue stays open; it never closes the bug.

## Standard authoring fast path (stop fan-out)

For standard prompt, Story, and scenario authoring, read ONLY `SKILL.md`, this `RUNBOOK.md`, `guide.md`, and `story-guide.md` (`< 35 KB` total). **Do NOT open `runbook/*.md`, `review.md`, `verification-*.md`, or `autopilot-job-rules.md` during standard authoring** unless you hit a specific named edge case in the router table below.

1. **Files and order (§1, §2, §22):** Write `user_stories/<story>.md` (`# Title`, one `As a <role>, I want <goal>, so that <reason>.` line, numbered `## Acceptance criteria`, optional bullet-only `## Rules to check`), plain-Markdown `prompts/<job>.prompt.md` (`<= 500` lines: purpose, `## Domain decisions`, named public operations with explicit input/result/error field names and types, failure edges, `## Dependencies`), and `tests/<story>.json` (`tests/runtime/<story>.json` or `test/runtime/<story>.json` when the repo keeps native tests in `tests/` or `test/`). Put separate user behaviors in separate Stories (`1` Story = `1` scenario file). Start `check`, `build`, `verify`, `formal`, and `review` subagents strictly in stage order after files exist on disk; wait once with a long timeout.
2. **Plain-Markdown prompts and `native-only` dependency direction (§2, §6, §7, §21):** Do not write an embedded `Runtime interface` block; `pdd test` synthesizes and caches interfaces lazily from prose and linked `$contract` schemas. Name every public operation (`operation` in `steps`) and every injected outside resource as `<port>.<op>` in prose (database, files, HTTP, clock, randomness, child processes) with explicit input and output fields. **Never link a `kind: native-only` adapter under `## Dependencies` of a checkable Story, domain, or screen prompt** (doing so marks the Story dependency closure `native-only`); invert the arrow so the `kind: native-only` boundary adapter depends on the checkable domain prompt.
3. **Scenario JSON (`tests/<story>.json`) and `simulation_overrides` (§2–§4, §8–§10, §18, §21):** Use `"schema_version": "prompt-runtime.program-scenario.v1"`, `"story_path": "user_stories/<story>.md"`, `"criteria": [{"id": "AC1", "text": "<exact Story line with straight quotes>"}]`, `"initial_world": {...}`, `"simulation": {...}`, and `"steps": [{"step_id": "s1", "entry_path": "prompts/<job>.prompt.md", "operation": "<op>", "input": {...}, "checks": [{"criterion_id": "AC1", "target": "result", "path": "/field", "op": "equals", "value": ...}]}]`. Check every criterion with an exact operator (`equals`, `not_equals`, `one_of`, `count`, `at_least`, `at_most`, `not_contains`, `all_in`, `equals_ignore_case`, or HTML `exists`). Keep scenarios `<= 15` steps and each step to 1 action or ~10 moves/rows/calls (`<= 10` minutes). Every integer is whole (`BigInt` safe); strings carry exact `\n` rules (`cli` entries take `{"argv": [...]}` and return `{exit_code, stdout, stderr}`). Every key in `simulation` or step `simulation_overrides` must be `<port>.<op>` named in the reachable prompt prose: reads use `"action": "fixture.lookup"` (`world_pointer`, `match_fields`, `key_pointer`, `found_pointer`, `result_value_pointer`, `result_template`); writes use `"action": "port.write"` (`write_mode`: `"append"` or `"put"`, `world_pointer` existing in `initial_world`, `record_fields` / `key_field`, `result_template`). A `simulation_overrides` failure binding also needs a checked `criterion_id` and an un-negated `failure_quote` substring from that criterion.
4. **Screens, `.ui.svg`, and local lint (§13, §20):** User-facing pages expose a `render` operation returning `{html}` (and optional structured facts), link `.ui.svg` mockups under `## Appearance`, and wire CSS under `"stylesheets"` in `app-map.json`. During authoring, run `pdd lint --local` (`<50ms`, zero AI/browser) to check `.ui.svg` XML, `viewBox`, labels, controls, regions, `simulation_overrides` port alignment, and `native-only` links; **do not render `.ui.svg` to PNG in a headless browser unless the person explicitly asks for PNG previews**. Run `pdd test` once (it includes hosted lint; never run `pdd lint` right before `pdd test`, and use `pdd test --read` instead of resending). Record genuine chat approval via `pdd approve ... --said` or `pdd workflow approve <run> --said - <<'PDD_SAID'`.
