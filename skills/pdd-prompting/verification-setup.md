# Real behavior verification setup

Use the approved Story as the behavior authority and the existing replay and checker rules for verdicts. This procedure supports the repository's start-up recipe; it does not replace those rules.

1. Inspect documentation, manifests, CI and tests for installation, running, data and existing checks. Identify the affected public boundary and reuse a working recipe when it covers it. Distinguish discovered facts from missing access or product decisions.
2. If needed, copy and fill in `verification-recipe.md` from this skill into the repository, adapting it to the project. Add the smallest repo-native entry point and controlled fixtures for this behavior. Keep the recipe and required source in the repository. Record prerequisites, preparation, isolated data and dependencies, start and readiness, the real action, expected visible results and meaningful side effects, evidence, and cleanup. Use isolated resources; do not require private conversation context.
3. For manual or general setup, before selecting issues run the applicable install/build and relevant tests, then run the recipe and the Story's action. For Autopilot: Before selecting issues, run documented bounded repository readiness commands, or use the installed CLI readiness already checked when applicable. Run example or template commands only when their paths exist and apply to this repository; retain any actual failure as evidence. After selection, run the applicable install/build and relevant tests, then run the recipe and the Story's action. Report any unavailable or inapplicable step and its reason. A CLI uses the real process and checks output, status and relevant files; a library uses a consumer of its public API; a service uses its protocol and required local dependencies; a web or desktop application uses the actual user action; static or data output is built and loaded in its relevant consumer. A new product stays in prompt space until code is authorized.
4. Map every required case to the existing Story criterion and case/test ID. Record each as passed, failed, blocked before target, skipped or unexecuted, and name the intended boundary actually reached. Report source/context, composition/dependencies, compilation, test collection, readiness, boundary execution and criterion checks as separate applicable stages; mark a stage not applicable with its reason. Compilation, collection or readiness alone is not a behavior pass.
5. Associate each attempt with the actual entry point and source modules or built artifact loaded by the process, the source revision or local diff, dependency lock and test helpers. Record local changes that affect loaded source; a revision label alone does not show what ran. Reuse identities the project already provides; do not add hash pins. Record the original failure and cleanup result. Keep cleanup errors visible and separate from the behavior result; cleanup must not erase the earlier failure or pass. A pre-target failure cannot prove a behavior defect or count as a mutation kill.
6. Report integration scope separately. An unavailable dependency, failure before the action, or unexecuted check is not a behavior pass. A simulated external dependency can support a narrower local claim, not a real integration pass. Keep prompt-interpreter outcomes separate from native execution.
7. A fresh independent verifier repeats the recipe from a fresh checkout, using controlled isolated data. Retain commands, candidate revision, explicit issue mapping, UTC execution time, verifier/session, evidence type, observed results and limitations in the existing run evidence outside the checkout; cleanup must not delete that evidence. Follow the existing replay and independent checker rules for evidence and verdicts.

For a bug, run the same intended expectation at the same boundary against old and corrected code. Show the old assertion failing for the claimed behavior and the corrected result passing. A pre-target crash or setup failure is a limitation, not proof of the semantic defect or a mutation kill. Do not weaken expected results to obtain a pass.
