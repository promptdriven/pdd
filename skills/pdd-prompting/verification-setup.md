# Real behavior verification setup

Use the approved Story as the behavior authority and the existing replay and checker rules for verdicts. This procedure supports the repository's start-up recipe; it does not replace those rules.

1. Inspect documentation, manifests, CI and tests for installation, running, data and existing checks. Identify the affected public boundary and reuse a working recipe when it covers it. Distinguish discovered facts from missing access or product decisions.
2. If needed, copy and fill in `verification-recipe.md` from this skill into the repository, adapting it to the project. Add the smallest repo-native entry point and controlled fixtures for this behavior. Keep the recipe and required source in the repository. Record prerequisites, preparation, isolated data and dependencies, start and readiness, the real action, expected visible results and meaningful side effects, evidence, and cleanup. Use isolated resources; do not require private conversation context.
3. Before selecting issues, run the applicable install/build and relevant tests, then run the recipe and the Story's action. Report any unavailable or inapplicable step and its reason. A CLI uses the real process and checks output, status and relevant files; a library uses a consumer of its public API; a service uses its protocol and required local dependencies; a web or desktop application uses the actual user action; static or data output is built and loaded in its relevant consumer. A new product stays in prompt space until code is authorized.
4. Report setup, executed behavior and integration scope separately. An unavailable dependency, failure before the action, or unexecuted check is not a behavior pass. A simulated external dependency can support a narrower local claim, not a real integration pass. Keep prompt-interpreter outcomes separate from native execution.
5. A fresh independent verifier repeats the recipe from a fresh checkout, using controlled isolated data. Retain commands, candidate revision, explicit issue mapping, UTC execution time, verifier/session, evidence type, observed results and limitations in the existing run evidence outside the checkout; cleanup must not delete that evidence. Follow the existing replay and independent checker rules for evidence and verdicts.

For a bug, run the same intended expectation against old and corrected code. Show the old assertion failing for the claimed behavior and the corrected result passing. A crash or setup failure on old code is a limitation, not proof of the semantic defect. Do not weaken expected results to obtain a pass.
