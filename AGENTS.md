# Working on PDD

Before you write or change a Story or a prompt, read the full [Prompting guide](skills/pdd/references/prompting.md) in this conversation. Follow its method for module ownership, public behavior, what must not change, required dependencies and the edge cases that matter. A link or a Story template is not enough. If you lose the context, read the guide again before you write. Before you write a Story, also read the full [Story guide](skills/pdd/references/stories.md).

Read [skills/pdd/SKILL.md](skills/pdd/SKILL.md) for the workflow and core rules. Prompts are the source: change the prompt that owns the behavior before you change the code. Keep expected cases apart from what the code returns. Review changes to the contract with the person. Never invent their decision. All canonical guides live directly under `skills/pdd/references/`.

What this package contains:

- One visible skill `skills/pdd/` (`SKILL.md` plus co-located on-demand guides in `skills/pdd/references/{prompting,stories,product,ports-and-cli,ui-and-screens,verification,formal}.md`; headless Autopilot worker rules live separately in `src/autopilot/job-rules.md`). People install skills with `pdd setup` (or `npx skills add promptdriven/pdd -g`). `pdd setup [--yes] [--skills-dir PATH] [--upgrade]` installs laptop-wide skills to `~/.agents/skills`, `~/.claude/skills` (or `$CLAUDE_CONFIG_DIR/skills`, skipping duplicates when a Claude Code plugin install is detected in `installed_plugins.json`), and `~/.gemini/config/skills`, and previews Simulator MCP registration for detected Codex, Claude Code, Gemini, and Antigravity configs (or with `--upgrade`, refreshes only already-registered stale MCP entries silently) without editing repositories or Autopilot settings. `pdd init` adds the 4-line `<!-- pdd:start -->`...`<!-- pdd:end -->` block to a repo's `CLAUDE.md` (else `AGENTS.md`) and detects the project's language and test command without editing root `.gitignore`. `pdd setup`, `pdd upgrade` (delegating post-upgrade sync to the installed binary's `pdd setup --upgrade`), and a once-per-version check on normal CLI commands (excluding discovery, `status`, `init`, `files`, and `--json` routes) recognize real PDD-managed user skill folders carrying `.pdd-skill.json` or `pdd-skills:` frontmatter (including `~/.codex/skills` and `$CODEX_HOME/skills`), replacing older or same-version differing copies with a `.pdd-skill.json`-marked copy and adding missing bundled skills. They remove PDD-managed directories of retired skills (`pdd-autopilot`, `pdd-check`, `pdd-merge`, `pdd-setup`, `pdd-prompting`, `pdd-small-change`, `pdd-bug`, `pdd-feature`, `pdd-product`, `pdd-graph`) and unlink retired symlinks that are dangling or point into another user agent skill directory. They never touch non-PDD skills, folders lacking both `.pdd-skill.json` and `pdd-skills:` frontmatter, or symlinks pointing into developer git checkouts. pdd never copies skills into the person's repo. Each `SKILL.md` has `pdd-skills: VERSION` under `metadata:` in its frontmatter: change it with the package version.
- People open Codex or Claude Code as usual and invoke `$pdd` in Codex or `/pdd` in Claude Code (routing `product`, `bug`, `feature`, and `small-change`). `pdd init` adds the 4-line block between `<!-- pdd:start -->` and `<!-- pdd:end -->` to `CLAUDE.md`, else `AGENTS.md`. It never pastes the guide.
- Agents run `pdd lint`, `pdd test`, native suites, and `pdd prove`. A fresh subagent that did not write the code verifies it. `pdd prove` runs offline lint, diff checks, repository tests, and `verify.paths` recipes (or `--test`/`--expect` bug contrast) against the base ref; pdd does not merge. Review and approve changed prompts in chat or GitHub PR review. Never invent a person's decision or decide expected values.
- Main agents merge only on an explicit person request. Follow [Prompting guide §5](skills/pdd/references/prompting.md#5-expected-values-approvals-and-merges). The operator’s explicit auto setup and start or an applicable standing delegation can supply that request; a configuration read alone cannot. In Autopilot `auto` mode, the core engine merges its own PR only after its own merge check passes; see [core engine](docs/cli.md#core-engine).
- `docs/cli.md` shows every command form of `pdd --help`. `test/docs-commands.test.mjs` fails when a form is missing, so update `docs/cli.md` with each change to the command catalog.
- The README and the docs describe pdd as it is today, as if this were the first version. Put history and change notes only in the GitHub release notes. The one exception is the short note for people who have the Python pdd installed. `test/docs-first-time.test.mjs` fails on history words.
- Agents start in full-access mode. `pdd setup` previews per-agent MCP config changes and asks y/N before writing them. pdd never copies credentials or edits repository files during `pdd setup`.

Keep the package self-contained: no credentials. Only `pdd test`, `pdd lint`, `pdd simulate` and the Try tools in `pdd mcp` call the PDD interpreter, with the user's gh token; the address is one setting (`PDD_RUNTIME_URL`, default `DEFAULT_RUNTIME_URL` re-exported through `src/runtime-seam.mjs` from `@promptdriven/runtime-client`). Do not import captured conversations or operational fixtures.

Each path has one active writer. Use a topic branch, keep other work and keep implementation prompts with their code. Use ordinary Node tests for changed public behavior. Avoid tests that only check prose or repeat the implementation. The public full suite is `npm test`. It needs no live service and no model call. A real agent run that the person asked for is a separate activity.

Report what changed, the real check results and any behavior that is not proved. In every PR into `main` that finishes an issue (including release or integration PRs), write one `Closes #N` line per completed issue; use `Refs #N` only when the issue still needs another PR. A local draft or PR summary is not publication. Keep execution notes outside the repository. Public source publication needs a review and a green public full suite. Follow the route of the named integrator. Never force-push, rewrite private repository history or publish a package to npm as a routine check.
